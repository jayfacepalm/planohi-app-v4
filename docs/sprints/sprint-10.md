# Sprint 10: Log Tracing, Email Masking & Activity Logs Audit

This sprint implements end-to-end trace correlation using MDC, enforces client-safe email masking at the API boundary and inside console logs, and establishes an Activity Logs microservice that consumes user action events from RabbitMQ and stores a structured audit trail in the PostgreSQL database.

---

## 1. Goals

1. **Correlation ID Log Tracing**: Standardize request tracing across the Next.js proxy, Spring Boot API, and background microservices (`email`, `activityLogs`) by propagating a unique 16-character alphanumeric identifier set in Logback MDC.
2. **Strict Email Masking**: Enforce data privacy by masking email addresses at the backend serialization boundary and within log files. Unmasked emails must never be sent to the client browser or written to system logs.
3. **Activity Logs Microservice**: Create a dedicated auditing container (`activityLogs`) that consumes event payloads from RabbitMQ durably and logs structured actions (login, registration, CUD (Create, Update, Delete), and email dispatches) in the database with JSON details.

---

## 2. User Stories

* **US-10.1 (Correlation ID Log Tracing)**: As a system maintainer, I want all logs generated by a single user transaction to carry a unique 16-character correlation ID, enabling easy request tracing across the Next.js server, Spring Boot backend, and async worker nodes.
* **US-10.2 (Strict Email Masking)**: As an invitee or curator, I want my email address to be strictly masked on the client UI and in the system log files (e.g. `t*****@***ple.com`), preventing unauthorized exposure of my email.
* **US-10.3 (Activity Audit Log)**: As an administrator, I want a persistent, structured history of all system activities (Registration, Login, Event and child entity CUD (Create, Update, Delete) operations, Email scheduling and dispatches), so that I can trace operational audits and modifications.

## 3. Technical & Database Design

### 1. MDC Correlation ID Flow
* **Generation**: The Next.js API proxy (`route.ts`) or server-side API client (`api-client.ts`) checks for an existing `X-Correlation-Id` header. If missing, it generates a random 16-character alphanumeric string and injects it as an HTTP header `X-Correlation-Id`.
  * **Alphanumeric Generator**: Cryptographically secure random alphanumeric string (character set: `A-Z`, `a-z`, `0-9`) to ensure collision safety.
* **API Interception**: A custom filter `CorrelationIdFilter` intercepts incoming calls in the Spring Boot backend, binds the ID to Logback's `MDC` context, and appends it to outgoing response headers.
* **Log Pattern**: The Logback pattern is updated to extract the MDC value: `[%X{correlationId}]`.
* **Propagation to RabbitMQ**:
  * Customize the `RabbitTemplate` configuration with a `MessagePostProcessor` that copies the active correlation ID from MDC to the message properties headers:
    ```java
    rabbitTemplate.setBeforePublishPostProcessors(message -> {
        String correlationId = MDC.get("correlationId");
        if (correlationId != null) {
            message.getMessageProperties().setHeader("X-Correlation-Id", correlationId);
        }
        return message;
    });
    ```
  * In the consumers (`email` and `activityLogs`), extract the header and bind it to MDC during queue listener invocation. An elegant AOP Aspect `@Aspect` intercepts `@RabbitListener` methods to manage MDC lifecycle automatically:
    ```java
    @Aspect
    @Component
    public class RabbitMdcAspect {
        @Around("@annotation(org.springframework.amqp.rabbit.annotation.RabbitListener)")
        public Object manageMdc(ProceedingJoinPoint pjp) throws Throwable {
            org.springframework.amqp.core.Message message = null;
            for (Object arg : pjp.getArgs()) {
                if (arg instanceof org.springframework.amqp.core.Message m) {
                    message = m;
                    break;
                }
            }
            if (message != null) {
                String correlationId = (String) message.getMessageProperties().getHeaders().get("X-Correlation-Id");
                if (correlationId != null) {
                    MDC.put("correlationId", correlationId);
                }
            }
            try {
                return pjp.proceed();
            } finally {
                MDC.clear();
            }
        }
    }
    ```

### 2. Email Masking Algorithm
* **Logic**:
  * **Local Part**: If length is greater than 1, preserve the first character and replace the remaining characters with `*` matching the length (e.g. `tester` -> `t*****`). If length is 1, keep it.
  * **Domain Name (before first dot)**: If length is greater than 3, replace the leading characters with `***` while keeping the last 3 characters (e.g. `example` -> `***ple`). If length is 3 or less, replace the entire domain name with `***` (e.g. `b.com` -> `***.com`).
  * **Suffix**: Retain standard suffixes intact (e.g. `.com`, `.org`, `.co.uk`).
  * **Robustness**: If email is null or doesn't contain `@`, return it unmodified.
* **Jackson Boundary Serialization**:
  * Create a custom Jackson serializer `MaskedEmailSerializer.class`:
    ```java
    public class MaskedEmailSerializer extends JsonSerializer<String> {
        @Override
        public void serialize(String value, JsonGenerator gen, SerializerProvider serializers) throws IOException {
            gen.writeString(MaskingUtil.maskEmail(value));
        }
    }
    ```
  * Annotate client-facing DTOs response fields:
    ```java
    @JsonSerialize(using = MaskedEmailSerializer.class)
    private String email;
    ```
    This applies to `UserDto.java`, `InviteeDto.java`, and `EventCuratorResponseDto.java`. Unmasked emails remain safe in the Postgres DB and JWT signatures, but are never serialized to REST responses.
* **Log Masking**:
  * To prevent developers or library logs from writing raw emails to standard output, write a custom Logback `MessageConverter`:
    ```java
    public class EmailMaskingConverter extends MessageConverter {
        private static final Pattern EMAIL_PATTERN = Pattern.compile(
            "[a-zA-Z0-9_+&*-]+(?:\\.[a-zA-Z0-9_+&*-]+)*@(?:[a-zA-Z0-9-]+\\.)+[a-zA-Z]{2,7}"
        );
        @Override
        public String convert(ILoggingEvent event) {
            String message = super.convert(event);
            if (message == null) return null;
            Matcher matcher = EMAIL_PATTERN.matcher(message);
            StringBuilder sb = new StringBuilder();
            while (matcher.find()) {
                String email = matcher.group();
                matcher.appendReplacement(sb, Matcher.quoteReplacement(MaskingUtil.maskEmail(email)));
            }
            matcher.appendTail(sb);
            return sb.toString();
        }
    }
    ```
  * Configure `logback-spring.xml` in all services to use this converter to clean log patterns dynamically. This ensures absolute safety at a minor performance cost.

### 3. Database Audit Table Schema
The Flyway migration script `V20260613143000__create_activity_log_table.sql` is stored centrally in the `api` module under `api/src/main/resources/db/migration`:
```sql
CREATE TABLE activity_log (
    id UUID PRIMARY KEY,
    correlation_id VARCHAR(16) NOT NULL,
    user_id UUID,
    user_alias VARCHAR(100),
    action VARCHAR(50) NOT NULL,
    entity_type VARCHAR(50),
    entity_id UUID,
    event_id UUID,
    status VARCHAR(10) NOT NULL,
    details JSONB, -- JSONB payload details for native indexing/querying
    timestamp TIMESTAMP WITH TIME ZONE NOT NULL
);

CREATE INDEX idx_activity_log_correlation_id ON activity_log(correlation_id);
CREATE INDEX idx_activity_log_event_id ON activity_log(event_id);
CREATE INDEX idx_activity_log_user_id ON activity_log(user_id);
```

### 4. Activity Logs Microservice Architecture
* **Exchange, Queues & DLX**:
  * Define a topic exchange `activity.exchange` and queue `activity.log.queue` bound with routing key `activity.#`.
  * Define a Dead Letter Exchange (DLX) `activity.exchange.dlx` and Dead Letter Queue (DLQ) `activity.log.dlq` to handle failed log operations safely.
  * Queue `activity.log.queue` is declared with arguments:
    * `x-dead-letter-exchange`: `activity.exchange.dlx`
    * `x-dead-letter-routing-key`: `activity.log`
* **JPA Hibernate 6 Mapping**:
  * In the `activityLogs` microservice, map the `details` JSONB column using Spring Boot / Hibernate 6 native `@JdbcTypeCode(SqlTypes.JSON)` annotation, avoiding the need for boilerplate custom converters:
    ```java
    @JdbcTypeCode(SqlTypes.JSON)
    @Column(name = "details", columnDefinition = "jsonb")
    private Map<String, Object> details;
    ```
* **Service Container**:
  * The `activityLogs` module acts as a dedicated microservice. Add its service block in `docker-compose.yml`:
    ```yaml
      activitylogs:
        build:
          context: ./activityLogs
          dockerfile: Dockerfile
        container_name: planohi-activitylogs
        environment:
          SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/${POSTGRES_DB:-planohidb}
          SPRING_DATASOURCE_USERNAME: ${POSTGRES_USER:-planohiuser}
          SPRING_DATASOURCE_PASSWORD: ${POSTGRES_PASSWORD:-planohipassword}
          SPRING_RABBITMQ_HOST: rabbitmq
          SPRING_RABBITMQ_PORT: 5672
        depends_on:
          db:
            condition: service_healthy
          rabbitmq:
            condition: service_healthy
        networks:
          - app-network
    ```
  * Create `activityLogs/Dockerfile` mirroring the `email/Dockerfile` structure.

## 4. API Backend Upgrades (Spring Boot)

### 1. Logging Pattern Configuration
Modify `logback-spring.xml` or `application.yaml` to define the console log formats:
```yaml
logging:
  pattern:
    console: "%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - [%X{correlationId}] - %msg%n"
```

### 2. CorrelationId Filter Implementation
* **Class**: `CorrelationIdFilter.java` (extends `OncePerRequestFilter`).
  * Checks for `X-Correlation-Id` header; generates a random 16-character alphanumeric string if missing.
  * Adds `correlationId` to MDC.
  * Sets the response header `X-Correlation-Id`.
* **Registration**: Add it to `SecurityConfig.java` to execute before `ApiKeyFilter`.

### 3. Email Masking Utility
* **Class**: `MaskingUtil.java` exposing `public static String maskEmail(String email)` in package `com.planohi.api.util`.

### 4. Activity Logs Event Publisher
* **Class**: `ActivityLogPublisher.java`
  * Exposes `publish(String action, String entityType, UUID entityId, UUID eventId, String status, Map<String, Object> detailsMap)`.
  * Fetches `userId`/`userAlias` from `SecurityContextHolder` `UserPrincipal`.
  * Fetches `correlationId` from MDC.
  * Publishes `ActivityLogEvent` to RabbitMQ.
* **Scope of Tracked Activities**:
  * **Design Constraint**: Read (GET) operations are explicitly excluded from auditing to avoid performance degradation and database storage flooding during user navigation and refreshes. Auditing is strictly confined to state-modifying actions (CUD) and critical security or transaction lifecycle events:
  * **Auth**:
    * `USER_REGISTER`: Registrations
    * `USER_LOGIN`: Logins
  * **Event CRUD**:
    * `EVENT_CREATE`, `EVENT_UPDATE`, `EVENT_DELETE`
  * **Child Entities CRUD**:
    * `COMPONENT_CREATE`, `COMPONENT_UPDATE`, `COMPONENT_DELETE`
    * `SPENDING_CREATE`, `SPENDING_UPDATE`, `SPENDING_DELETE`
    * `TIMELINE_ITEM_CREATE`, `TIMELINE_ITEM_UPDATE`, `TIMELINE_ITEM_DELETE`, `TIMELINE_ITEM_TOGGLE`
  * **Invitations & Curators**:
    * `INVITEE_CREATE`, `INVITEE_UPDATE`, `INVITEE_DELETE`
    * `INVITEE_RSVP_SUBMIT`: RSVP response submission
    * `CURATOR_INVITE`: Inviting curator
    * `CURATOR_ROLE_UPDATE`: Modifying role
    * `CURATOR_REMOVE`: Removing curator
  * **Emails**:
    * `EMAIL_DISPATCH_SCHEDULE`: Quartz scheduling
    * `EMAIL_DISPATCH_CANCEL`: Cancelling schedule
    * `EMAIL_DISPATCH_TRIGGER`: Dispatched invite

* **Proxy**: Update [route.ts](/planohi-app-v4/web/app/api/proxy/%5B...path%5D/route.ts) to check for `X-Correlation-Id`. If missing, generate a 16-character alphanumeric code using a cryptographic random function and append it to headers.

### 2. Strictly Masked View Binding
* Ensure all form views (e.g. Guest listings, curator grids) bind directly to the returned masked email values.
* During update actions, if the field is not modified, do not send the masked email to the backend. If the organizer changes the email, send the new unmasked value.
